сайт и редактор

Этот документ объясняет, как устроен сайт A.LAB, как пользоваться внутренним редактором, что нужно для запуска редактора в сети, как безопасно вносить изменения через AI-агентов и как публиковать обновления.

one-page Сайт собран как цельная лендинговая история с секциями, кейсами и контактами.
cms Редактор управляет кейсами, медиа, SEO-полями, настройками карточек, аудио и статистикой.
deploy Публичный сайт деплоится как статическая сборка, редактор требует отдельного backend.
agents Codex и Antigravity можно использовать для аккуратных правок дизайна, кода и деплоя.

01 / архитектура

что представляет собой сайт

A.LAB — это не шаблонный сайт с набором карточек, а интерактивная презентация агентства: бренд, эмоциональная инженерия, принципы работы, кейсы и быстрый контакт. Публичная часть собрана как Vite-сайт, а контент кейсов подключается из JSON, который формирует редактор.

Публичный сайт

Главный экран с интерактивным логотипом, блоки о подходе, принципы, кейсы, контакты, QR и плавающий контактный блок.

index.html main.js css/sections

Редактор

Внутренняя CMS для проектов, настроек, медиа, SEO, статистики и предпросмотра кейсов.

editor/server.mjs editor/public editor/cms.db

Данные

Публичный сайт читает опубликованные проекты из public/data/cases.json. Черновики остаются только в редакторе.

cases.json settings.json public/images
Важная логика публикации: проект появляется на сайте только если в редакторе у него статус “Опубликован”. Черновики можно готовить спокойно, не показывая их посетителям.
02 / дизайн-процесс

памятка для дизайнеров

Сайт построен на спокойной серой базе, крупной типографике Unbounded и мягких стеклянных поверхностях. Для новых кейсов важно сохранять визуальный язык: меньше декоративного шума, больше воздуха, четкие логотипы, аккуратные медиа и понятная иерархия.

Что готовить Рекомендация Почему это важно
Логотип кейса SVG предпочтительно. PNG/WebP допустимы, если фон прозрачный и есть запас по размеру. Карточки портфолио показывают логотип крупно, без дополнительного названия сверху.
Изображения Горизонтальные hero-кадры 1600-2400 px, WebP/JPG. Не загружать исходники на 20-50 MB без нужды. Сайт должен быстро открываться на мобильных и не терять качество на больших экранах.
Тексты Короткие заголовки, ясные подписи, без длинных абзацев в карточках и компактных панелях. Визуальная система держится на плотной, но легкой подаче информации.
Цвета Использовать сдержанные акценты. Не превращать секцию в один доминирующий цвет. Бренд A.LAB должен оставаться главным, а кейсы — аккуратно раскрывать портфолио.
Мобильная версия После каждой крупной правки проверять ширины 390-430 px и 768 px. Большая типографика и карточки требуют отдельной проверки на переносы и наложения.

Хороший кейс

Есть логотип и понятная категория.
Есть 1-2 сильных визуальных кадра.
Текст говорит о задаче, подходе и результате.
SEO-title и SEO-description заполнены.

Чего избегать

Размытые картинки, скриншоты с лишними рамками, водяные знаки.
Слишком длинные названия в карточках и блоках.
Медиа без оптимизации, тяжелые видео без необходимости.
Правки напрямую в JSON без бэкапа.
03 / редактор

как пользоваться редактором

Редактор запускается отдельно от публичного сайта. Локальный адрес по умолчанию: http://localhost:3001/cms-3001/. Логин и пароль задаются в файле .env и должны передаваться ответственным сотрудникам отдельно, не внутри этого документа.

Запуск локально

В терминале из папки проекта запустить редактор:

npm run editor

После запуска открыть http://localhost:3001/cms-3001/.

Вкладка “Проекты”

Здесь создаются, дублируются, импортируются и сортируются кейсы. Категории можно переименовывать, но лучше не менять их ID без разработчика.

  • На сайте — проект опубликован.
  • Черновик — проект хранится в редакторе, но не попадает в публичный JSON.
  • JSON — экспорт конкретного кейса для передачи или архива.

Редактирование кейса

Внутри кейса можно менять название, категорию, логотип, внешний URL, SEO-поля и набор блоков.

  • Для простого кейса использовать блоки “Заголовок”, “Текст”, “Изображение”, “Галерея”.
  • Для ссылок на Behance, Telegram, сайт проекта использовать блок “Ссылки”.
  • Для числовых результатов использовать блок “Метрики”.
  • После правки смотреть live-preview в desktop/mobile режимах.

Настройки сайта

В этой вкладке настраиваются звуки букв логотипа, Figma token для импорта, внешний вид карточек и параметры интерфейса.

Figma token нужен только если команда реально импортирует изображения из приватных Figma-файлов. Его нельзя хранить в публичных документах.

Статистика

Вкладка показывает first-party аналитику: просмотры, визиты, источники, устройства, секции, внешние клики и базовый SEO-чеклист.

Страны появятся на хостинге, который передает geo-заголовки. VPN без внешней IP-базы определяется честно как unknown.

Перед массовыми правками контента сделать бэкап: editor/cms.db, public/data/cases.json, public/images и public/data/settings.json.
04 / сеть

как запустить редактор в сети

Сейчас редактор работает локально на компьютере разработчика. Чтобы сотрудники заходили по адресу вроде https://cms.alabspace.com, нужен постоянный backend с диском или базой данных. Обычный статический деплой сайта на Vercel для этого недостаточен.

Временно бесплатно

Cloudflare Tunnel может открыть локальный редактор наружу. Это удобно для демонстрации, но компьютер должен быть включен.

Подходит: показать заказчику, быстро согласовать правки.

Рабочий вариант

VPS, Render, Railway или Fly.io с постоянным диском. Текущий Express + SQLite можно развернуть с минимальными изменениями.

Подходит: сотрудники работают регулярно.

Serverless-вариант

Переделать хранение на Supabase, Cloudflare D1/KV/R2 или другую managed-базу.

Подходит: если нужен полностью облачный стек без сервера.

Минимальные требования для сетевого редактора

Домен или поддомен, например cms.alabspace.com.
HTTPS-сертификат. На VPS это обычно Caddy/Nginx + Let's Encrypt.
Постоянный диск или база для editor/cms.db и загруженных файлов.
Переменные окружения: CMS_LOGIN, CMS_PASSWORD, CMS_BASE_PATH, ANALYTICS_SALT.
Автобэкапы базы и папки public/images.
Ограничение доступа: сложный пароль, IP allowlist, VPN или Cloudflare Access.
Рекомендация: для надежной работы команды выбрать маленький VPS/Render/Railway и вынести редактор на cms.alabspace.com. Публичный сайт при этом может продолжать деплоиться отдельно как статическая сборка.
05 / AI-агенты

как менять сайт через Codex и Antigravity

AI-агенты полезны для правок верстки, анимаций, адаптива, текста, CMS и деплоя. Главное — давать им конкретную задачу, просить сначала изучить код, не перетирать чужие изменения и обязательно проверять сборку.

Когда использовать редактор

  • Добавить или скрыть кейс.
  • Заменить логотип, картинку, видео.
  • Поменять текст блока кейса.
  • Заполнить SEO-поля проекта.
  • Поменять карточные настройки, если они доступны в CMS.

Когда использовать агента

  • Изменить общий дизайн сайта или адаптив.
  • Добавить новый тип блока в CMS.
  • Починить баг, который повторяется.
  • Добавить интеграцию, аналитику или деплой.
  • Проверить производительность, SEO, консольные ошибки.

Безопасный сценарий работы с агентом

Подготовить задачу

Приложить скриншот, описать что именно изменить и где находится проблема. Хорошая формулировка: “в секции контактов на мобильной версии форма должна быть напротив заголовка, проверь 390 и 1440 px”.

Попросить агента изучить код

Агент должен найти существующие файлы и стиль проекта, а не писать новую архитектуру поверх старой.

Сначала найди файлы секции, посмотри текущие стили и только потом внеси минимальные правки.

Проверить локально

После правок агент должен запустить сборку и, если менялся интерфейс, открыть локальный сайт.

npm run build
npm run dev
npm run editor

Принять или откатить

Если правка не подходит, просить агента исправить конкретный результат, а не “сделать красиво”. Чем точнее обратная связь, тем быстрее будет хороший итог.

Примеры задач для Codex или Antigravity

Нужно поправить мобильную версию секции contacts.
Проверь текущие CSS/JS, внеси минимальные изменения, не трогай портфолио.
После правки запусти npm run build и проверь локально 390px и desktop.
Добавь в редактор новый тип блока "timeline".
Он должен сохраняться в SQLite/JSON, редактироваться в CMS и рендериться в кейсе.
Сначала изучи существующие блоки, затем реализуй по их паттерну.
Подготовь production deploy.
Проверь npm run build, проверь dist, затем сделай preview deploy.
Не выкладывай секреты и не коммить .env.
06 / публикация

деплой и публикация

Публичный сайт можно деплоить отдельно от редактора. Перед деплоем важно синхронизировать контент, проверить сборку, мобильные экраны, SEO и базовые клики. Редактор, если он нужен онлайн, деплоится как отдельный backend.

Публичный сайт

Команды для проверки и сборки:

npm install
npm run build
npm run dev

Если используется Vercel CLI:

npx vercel
npx vercel --prod

Редактор

Локально:

npm run editor

В сети: поднять Node/Express-сервер, подключить постоянный диск или managed-базу, настроить домен и HTTPS.

Чек-лист перед production

Открыть главную страницу и проверить первый экран, логотип, кнопку “Бриф”.
Проверить меню в контактном blob: “о нас”, “эмоциональная инженерия”, “принципы”, “кейсы”.
Проверить портфолио: категории, карточки, логотипы, внешние ссылки.
Проверить мобильные размеры 390-430 px и планшет 768 px.
Проверить консоль браузера: не должно быть критичных ошибок.
Проверить SEO: title, description, canonical, og:image, sitemap.xml, robots.txt.
Проверить, что .env и токены не попали в публичный репозиторий или сборку.
Если контент менялся через локальный редактор, убедиться, что после сохранения обновился public/data/cases.json. Именно этот файл читает публичный статический сайт.
07 / эксплуатация

поддержка и безопасность

У сайта есть две зоны ответственности: публичная витрина и внутренний редактор. Витрина должна быть быстрой и стабильной, редактор — защищенным и регулярно бэкапиться.

Еженедельно

  • Проверить сайт с телефона.
  • Посмотреть статистику посещений.
  • Проверить формы и ссылки.

Перед правками

  • Сделать бэкап базы и изображений.
  • Создать отдельную ветку или копию.
  • Записать, что именно меняется.

После правок

  • Запустить npm run build.
  • Проверить локально и на preview.
  • Сделать production deploy.

Файлы, которые важно беречь

Файл или папка Что хранит Как обращаться
.env Логин, пароль, секреты. Не публиковать, не отправлять в общий чат, хранить в менеджере паролей.
editor/cms.db База редактора: проекты, категории, статистика. Бэкапить перед крупными изменениями.
public/images Загруженные изображения и логотипы. Не чистить вручную без проверки, что файлы не используются.
public/data/cases.json Публичные опубликованные кейсы. Редактировать через CMS, руками только в исключительных случаях.
public/data/settings.json Настройки сайта: аудио, карточки и другие параметры. После изменения проверять публичный сайт.
08 / pdf

как сделать PDF из этого HTML

Документ сверстан как печатный HTML. Его можно открыть в браузере и сохранить в PDF без дополнительных программ. Для лучшего результата включить печать фона.

Открыть файл

Открыть docs/customer-guide.html в Chrome, Safari или Edge.

Печать

Нажать Cmd + P на macOS или Ctrl + P на Windows.

Настройки PDF

Формат A4, масштаб 100%, включить “Background graphics” / “Печатать фон”, поля стандартные или минимальные.

Сохранить

Выбрать “Save as PDF” / “Сохранить как PDF”. Перед отправкой заказчику пролистать файл и проверить переносы.
