# A.LAB — сайт alabspace.com

> Передача проекта студии — что где живёт, что ещё чинить: [docs/handover.md](docs/handover.md)

Живой сайт: **https://alabspace.com**. Всё, что попадает в ветку `main`, автоматически
собирается и выкладывается на сайт (GitHub Actions → GitHub Pages), обычно за 1–2 минуты.

## Статус локальной интеграции формы

- Основное русскоязычное написание бренда подтверждено: «алаб».
- Backend формы локально готов: `86 PASS / 0 FAIL`.
- Frontend contact-form/consent suite проверен: `13 PASS / 0 FAIL`.
- Frontend использует состояния `idle / sending / success / failure` и не имитирует успех.
- URL обработчика используется только при одновременных `VITE_FORM_DELIVERY_ENABLED=true` и заполненном `VITE_FORM_ENDPOINT`; текущая production-сборка принудительно оставляет доставку выключенной, поэтому введённые данные не отправляются и не очищаются.
- Поля `messenger` и `industry` подтверждены Заказчиком, входят в подготовленный payload и полный email будущей заявки.
- Текст согласия и серверные доказательства используют редакцию `12.10.2026`.
- Код целей и consent-gated загрузки счётчика `108408263` сохранён, но текущая production-сборка принудительно задаёт `VITE_YANDEX_METRIKA_ENABLED=false`.
- Deployment Yandex Cloud, реальные SMTP/Telegram и production smoke test не выполнялись.

Контент меняется не в коде, а в локальном редакторе (CMS). Как им пользоваться —
подробная инструкция в [docs/customer-guide.html](docs/customer-guide.html)
(скачать файл и открыть в браузере).

## Первый запуск на новом компьютере

Нужны Node.js 20+ и git.

```bash
git clone https://github.com/DenisDaraganGarden/alab-portfolio.git
cd alab-portfolio
npm install
cp .env.example .env
```

В `.env` обязательно поставить **свои** логин и пароль (в `.env.example` значения
намеренно пустые):

```
CMS_LOGIN=свой_логин
CMS_PASSWORD=свой_пароль
```

Без заданной пары логин/пароль редактор специально не запускается: этот же редактор
публикует сайт в интернет. Если работаете одна на своём компьютере и пароль не нужен —
вместо логина с паролем раскомментируйте в `.env` строку `CMS_SKIP_AUTH=1`.

Запуск:

```bash
npm run editor
```

Открыть <http://localhost:3001/cms-3001/>. Редактор виден только с вашего компьютера.

## Публикация

Кнопка «Опубликовать» в редакторе сама делает коммит и `git push` в `main`, дальше сайт
пересобирается сам.

Чтобы пуш прошёл, git должен знать ваш GitHub-аккаунт. Один раз:

```bash
gh auth login
```

(или любой привычный способ авторизации git по HTTPS).

Три правила, иначе публикация откажется работать:

- публиковать можно только из ветки `main` — `git checkout main`;
- перед началом работы сделать `git pull`, иначе редактор увидит на GitHub более новые
  изменения и остановится;
- не публиковать вдвоём одновременно.

## Что общее, а что только у вас

- Общее: опубликованное — `public/data/cases.json`, картинки `public/images`, звук `public/audio`.
- Только у вас: база редактора `editor/cms.db` и черновики. В репозиторий они не попадают.
- При первом запуске пустая база сама наполнится из `public/data/cases.json` — вы сразу
  увидите текущий сайт и сможете его править.

## Правки в коде (а не в контенте)

```bash
npm run dev      # локальный сайт с горячей перезагрузкой
npm run build    # проверить, что сборка не сломана
```

Минимальные тесты frontend submission logic без внешних отправок:

```bash
node --test test/contact-form.test.js
```

Baseline backup и журнал контрольного восстановления создаются вне репозитория в `delivery/backup`; SQLite DB при первом запуске CMS генерируется заново из `public/data/cases.json` и не является копией прежней базы Заказчика.

Код меняем в отдельной ветке и через Pull Request. `main` держим рабочей — из неё едет
живой сайт.
